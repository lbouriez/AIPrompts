# Prompt 02 — Faithfully implement the approved design

**Status: NOT VALIDATED.** Execute this implementation task; do not generate a new design proposal or another report.

## Mission

Act as a senior frontend engineer and visual QA specialist.

Implement the user's approved Design Studio option into the real application, or correct an implementation already started. **The approved prototype is the visual specification, not inspiration.** Preserve real behavior and verify the rendered result against the approved reference.

Do not rerun discovery, regenerate the alternatives, blend rejected directions, or independently simplify the selected design. No new Markdown reports. No deployment, commits, pushes, paid services, destructive data operations, or production-account changes without separate authorization.

## Inputs and compatibility

Resolve these from the user's instruction and actual project:

- Target application repository and its repository-specific rules.
- Studio location, normally `design-review/`.
- Explicitly approved option, revision, scope, and exceptions.
- Site mode: **existing by default**; `new` only when explicitly selected through the new-site starting point.
- Implementation mode: fresh, reconciliation, or auto-detect.

Inspect Git status and preserve unrelated work. Read the studio source, assets, tokens, screenshots, task data, and manifest when present. Old audit documents are supporting context only.

Inspect the real target application's source code and architecture, including routes, components, styles, configuration, and integrations, before editing. Browser rendering complements source inspection; screenshots alone are insufficient. If the target repository or approved prototype source is unavailable, request the missing access before implementation. Application changes, studio data, and verification evidence belong in the target repository, never in the prompt library.

**Legacy support:** the studio may have been generated by the earlier Prompt 1.5 and may lack `design-manifest.json`. Inspect its actual option code and recover the minimum route, token, asset, state, and approval data into a small structured file in the studio. Do not regenerate the mockups or ask the user to repeat the audit. A missing manifest is not a reason to restart.

If the approved option cannot be located or the user's choice is genuinely unknown, stop before design-changing edits and ask only for the missing reference/selection. Do not guess that the recommended option is approved.

## 1. Establish the exact implementation target

Identify the actual files that define the selected option: components, CSS, tokens, fonts, images, copy, layout, responsive rules, interaction states, and prototype URLs.

Record the explicit user approval and page/state scope. Freeze the selected visual reference using a revision identifier and source hashes or an equivalent reproducible snapshot, including imported shared styling/assets that affect its appearance. Capture reference screenshots before changing application code. Keep the original prototype untouched throughout implementation.

If the reference appears to have changed since the user's approval, flag that uncertainty; do not quietly approve the convenient current version yourself.

For an existing site, map approved prototype pages/templates to existing routes and components. For a new site, map them to the approved initial route structure and stack. Show coverage gaps instead of treating a homepage mockup as approval to invent an entire site.

For repeated pages, apply the approved template only where the scope supports it. Keep unapproved distinct templates unchanged on existing sites. For new sites, mark unapproved pages as not implemented; do not silently expand the launch scope.

Write a short implementation sequence into the studio's existing task data, not into a new report. Link each task to its target route, reference, relevant issue IDs, and acceptance criteria.

## 2. Detect fresh implementation versus reconciliation

Inspect current application code and the rendered website before deciding what to change.

**Fresh implementation:** introduce the approved visual system incrementally, adapting existing architecture and preserving behavior.

**Reconciliation:** an earlier attempt already exists. Keep correctly implemented work. Capture its current state, identify deviations from the approved prototype, and fix them in place. Do not revert unrelated improvements, overwrite user changes, or restart the application from a mockup.

If the original pre-redesign screenshots are unavailable, label the before view “current implementation before reconciliation.” Do not misrepresent it as the original website.

For a new site, use the approved stack and establish only the application foundation and features actually authorized. Missing backend or external integrations are dependencies, not permission to invent successful behavior.

## 3. Preserve functional contracts

Before editing, identify applicable contracts: routes and deep links; forms and server validation; authentication; pricing and checkout; subscriptions; search/filtering; locale switching; consent; analytics events; API calls; loading/error states; and access controls.

Preserve these behaviors, accurate business information, and SEO-critical URL/metadata behavior unless an approved requirement changes them. Do not replace real controls with decorative mockup buttons or simulated success messages.

Prototype fixtures are for the studio. Connect real application components to actual existing data and services, keeping types, validation, error handling, and server/client boundaries intact. For new integrations, use approved test environments and visibly report missing credentials or backend work. Never put secrets in client code or evidence.

If exact appearance conflicts with security, accessibility, truthful content, or essential functionality, preserve the necessary behavior and expose the conflict. Make only the minimal necessary deviation, record it, and do not count it as visually accepted without user review. Seek approval before material nonessential design changes.

Do not perform real purchases, send live messages, or modify real accounts to test a flow.

## 4. Implement by reusing the actual design

Prefer porting/adapting the approved presentational components, tokens, assets, and content over reconstructing them from a description. Integrate them into the application's normal architecture rather than shipping the studio or importing its entire runtime into production.

Match all meaningful design dimensions:

- Section order, page composition, grids, columns, containers, and content density.
- Header, footer, navigation, mobile menu, and sticky behavior.
- Exact fonts where licensed/available, type scale, weights, line heights, and heading wrapping.
- Colors, surfaces, borders, radii, shadows, icon styles, and spacing.
- Image identity, aspect ratios, cropping, placement, and loading behavior.
- CTA text, prominence, placement, states, and destination.
- Forms, cards, representative error/loading/success states, and responsive transitions.
- Approved copy and supported locale behavior.

Do not silently substitute imagery, drop sections, shorten approved copy, swap fonts, or copy from rejected options. If an approved asset is missing or unavailable, expose the dependency and ask for an alternative rather than pretending a substitute is the same design.

Use reusable components and existing conventions. Avoid broad refactors, framework migrations, new UI libraries, and dependency upgrades unrelated to implementing the approved design.

Keep the basic site accessible and responsive now; do not defer obvious keyboard, labeling, or mobile defects to Step 3. Preserve technical SEO fundamentals now; Step 4 is not permission to break them first.

## 5. Compare the rendered pages, not just source code

Run the approved prototype and the actual application. Capture matching pages and states at the reference sizes, normally:

- 1440 × 900 desktop.
- 390 × 844 mobile.
- 768 × 1024 tablet, plus widths around responsive transitions.

Use the same browser/environment, viewport, device pixel ratio, locale, theme, content, and UI state. Wait for fonts and images to load. Stabilize animations and dynamic fixtures for screenshot comparison, then test the real interactions separately. Record any unavoidable data differences rather than hiding them.

For every approved page/template:

1. Show approved reference beside actual implementation, with optional overlay/diff.
2. Inspect section by section: macro layout first, then type, assets, spacing, and states.
3. Record material mismatches with route, viewport, screenshot, and correction.
4. Fix the application and capture again.
5. Repeat until no material unapproved mismatch remains, or report a concrete blocker.

Use screenshot tooling already available; add a lightweight test setup only when justified. Automated image differences support review, not replace it. Browser rendering variations can prevent literal pixel identity, so report the comparison conditions and judge meaningful differences honestly.

Do not create a passing reference from the incorrect implementation. Do not edit the approved mockup to match your output, broadly mask differences, raise tolerances to hide defects, or overwrite baselines indiscriminately. Any narrow tolerance/mask must have a documented reason in the verification data.

If browser tools are unavailable, complete what can be checked from code but mark visual fidelity **not verified**. Do not present successful compilation as proof that the result matches.

## 6. Verify functionality and code quality

Run the existing relevant build, lint, type, unit/integration, and end-to-end checks. Add focused regression coverage where useful. Separate pre-existing failures from newly introduced ones.

Test the main user journeys safely, including mobile menu, links, forms/validation, auth entry points, language switching, and applicable error/loading states. Preserve analytics/consent behavior without sending misleading test conversions into production analytics.

Inspect console/network errors, missing assets, hydration problems where applicable, and all relevant responsive states. Confirm that studio code, rejected option assets, demo fixtures, and private evidence are not included in the public production build.

When a check is blocked, state why and what remains unverified. Do not weaken or remove a test just to turn it green.

## 7. Update the visual handoff and stop

Append implementation status, task results, comparison evidence, test commands/results, deviations, and remaining blockers to the existing studio data and its comparison/verification view. Keep the selected prototype and approved reference unchanged. Do not build a second dashboard or generate Markdown reports.

Use an explicit status: **implemented and visually verified**, **implemented with pending verification**, or **incomplete/blocked**. User acceptance is separate; do not approve your own visual deviations on the user's behalf.

End with a concise summary covering:

- Approved option/revision and actual pages implemented.
- Fresh implementation or reconciliation, and what changed.
- Exact application/studio launch commands and verified or clearly labeled expected URLs.
- Approved-versus-actual screenshots or exact evidence paths.
- Tests performed, remaining differences, and untested coverage.

Stop for visual review before Step 3. Do not claim an exact match, full completion, or production readiness when material deviations or critical unknowns remain. Do not deploy.

## Technical reference

When using screenshot automation, consult the current official documentation for the installed tool/version. For Playwright, start with [Visual comparisons](https://playwright.dev/docs/test-snapshots). Treat same-environment baselines and explicit review of changes as part of the verification process.
